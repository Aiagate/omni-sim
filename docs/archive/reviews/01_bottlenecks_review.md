# アーキテクチャ分析レポート: Deep Juno

現状の `omni-sim` のコードベースと、今後の拡張案（提案03: 惑星環境など）を踏まえたアーキテクチャ的な評価をまとめます。

## 1. スケーラビリティのボトルネック

### 貿易システムの計算量
[trade.rs](file:///home/dorothy/repos/omni-sim/src/systems/trade.rs) における `trade_system` は、現在「貿易ルートの数 × 資源の種類」でループしています。
- **懸念**: 惑星数が増え、全結合に近い貿易網が構築されると計算量が指数関数的に増加します。
- **特に非効率な点**: ループ内で `nation_query.iter().find(...)` を使用しており、これは各ルートごとに全国家を走査するため、全体で `O(N_routes * N_nations)` の計算量になっています。惑星数が増えると顕著な遅延の原因になります。

### シミュレーションイベントの流量
[simulation_event.rs](file:///home/dorothy/repos/omni-sim/src/components/simulation_event.rs) を通じたドメインと表示の分離は優れていますが、
- **懸念**: 貿易の個別の移送ごとに `SimulationEvent::TradeTransfer` を発行しています。数千のルートがある場合、1 Tick あたりのイベント数が膨大になり、TUIのイベントコレクターや描画処理がボトルネックになる可能性があります。

## 2. 拡張性・柔軟性の不備

### ハードコードされた初期化処理
[world_init.rs](file:///home/dorothy/repos/omni-sim/src/plugins/world_init.rs) は現在、地球やプロキシマbのデータを完全にハードコードしています。
- **懸念**: 惑星環境の多様化や、ランダム生成・シナリオ読み込みに対応する際、現在の構造ではコードの修正が必要になります。データ駆動型（JSON/YAML等からのロード）への移行が推奨されます。

### マジックナンバーの散在
[economy.rs](file:///home/dorothy/repos/omni-sim/src/systems/economy.rs) などに `0.00001` (食料消費率) といった定数が直接記述されています。
- **懸念**: バランス調整や、技術による消費効率の改善を実装する際、これらの数値が分散していると保守が困難になります。`SimulationConfig` や定数定義への集約が必要です。

### 技術（TechnologyState）の管理単位
[technology.rs](file:///home/dorothy/repos/omni-sim/src/components/technology.rs) は現在 **惑星（Planet）** ごとに付与されています。
- **懸念**: 1つの国家が複数の惑星を持つようになった場合、技術を惑星ごとに研究するのは不自然です。技術は **国家（Nation）** に紐付けるか、国家間で共有されるリソースとして管理すべきです。

### 惑星環境コンポーネントの肥大化
提案03で検討されている `PlanetaryEnvironment` は非常に多くのフィールドを持ちます。
- **懸念**: Bevy の ECS において巨大なコンポーネント自体は許容されますが、すべての惑星が常にすべての環境データを持つ必要があるかは検討の余地があります（例: 質量や重力は不変だが、大気や温度はテラフォーミングで変動する。これらを `StaticPlanetData` と `DynamicPlanetEnv` に分けるなど）。

## 3. 推奨される改善ステップ

1.  **データ駆動化**: 惑星や国家の初期パラメータを外部設定ファイルからロード可能にする。
2.  **空間的最適化**: 貿易システムの O(N^2) ループを改善するため、近接惑星間のみの貿易を効率的に抽出する仕組み（空間インデックスなど）を検討する、または検索処理をリソースやキャッシュで最適化する。
3.  **定数の集約**: 数式に使用される係数を `SimulationConfig` に移行し、技術やイベントで動的に変更可能にする。
4.  **エンティティ関係の再整理**: 技術や外交メモリを「惑星」ではなく「国家」に集約し、惑星は純粋に居住環境と資源産出の場として定義する。
