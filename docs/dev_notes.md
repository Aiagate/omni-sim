# 開発における課題と教訓 (Lessons Learned)

今回の改修（Mockモードの削除とMock Backendの実装）において、いくつかの技術的なハードルに直面しました。今後の開発の参考として、ここでそれらを記録しておきます。

## 1. Node.js の ESM vs CommonJS 競合
*   **問題**: 最初に `require()` を使用して `mock-server.js` を作成しましたが、`web/package.json` に `"type": "module"` が指定されていたため、実行時に `ReferenceError: require is not defined` が発生しました。
*   **教訓**: Vite や現代的なフロントエンド環境では `import/export` (ESM) が標準となっているため、補助スクリプトも ESM 形式で記述するか、拡張子を `.cjs` にする必要があります。

## 2. WebSocket のホストバインド問題
*   **問題**: デフォルトでは `localhost` でリッスンしていましたが、IPv4/IPv6 の解決設定によってはブラウザから接続できないケースがありました。
*   **解決**: WebSocket サーバーを明示的に `0.0.0.0` にバインドし、クライアント側（SimulationClient）からも `127.0.0.1` を優先的に使用するように指定することで、接続の確実性を向上させました。

## 3. ポートの競合とプロセス管理
*   **問題**: `EADDRINUSE: address already in use :::8080` エラーが多発しました。これは、以前のテストで起動したバックグラウンドプロセスがポートを掴んだまま残っていたためです。
*   **解決**: `fuser -k 8080/tcp` を使用して強制的にポートを解放する手順を検証フローに組み込みました。また、`nohup` を使用してバッググラウンドでの生存性を確保しました。

## 4. 検証環境特有の制限
*   **問題**: ブラウザのサンドボックス（自動テスト用サブエージェント）の制限により、WebSocket 接続が「正常に動作しているはずなのに切断される」という事象が発生しました。
*   **対応**: ブラウザ上での目視だけでなく、ワークスペース内蔵の `test-connection.js` （Node.jsベースのクライアント）を使用して、通信自体が正常であることをクロスチェックしました。これにより、「UI側の描画問題」と「通信路の問題」を切り分けることができました。

---
> [!TIP]
> 開発環境を再起動した際は、まず `lsof -i :8080` で古いプロセスが残っていないか確認することをお勧めします。
