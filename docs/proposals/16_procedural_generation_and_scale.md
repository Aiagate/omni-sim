# 提案 16: 星系生成の拡張とスケーラビリティ対策

## 概要

現在実装されている「星系の自動生成」機能を拡張し、実用的な惑星データの生成を行うとともに、星系・惑星数が増加した際 ($N \approx 50 \sim 100$) のパフォーマンス問題を解決するためのアーキテクチャ改良を提案する。

---

## 1. 現状の実装と課題

### 1-1. 星系/惑星のSeed生成
- **現状**: `src/plugins/world_init.rs` にて、Seed値 (`SimulationConfig.seed`) を元に `ChaCha20Rng` で50個の `PotentialSystem` を生成している。
- **課題**: 生成されるのは「位置」と「名前」のみで、** `planets` 配列が空**である。
  - `src/systems/exploration.rs` で星系を発見しても、中身のない空の星系 (`StarSystem` エンティティのみ) が生成される。
  - これでは新規に発見した星系に入植したり、資源を利用したりすることができない。

### 1-2. 有限マップの扱い
- **現状**: `GalaxyConfig` (デフォルト半径 100.0) に基づき、その範囲内に座標を生成している。
  - 明示的な「見えない壁」はなく、座標自体は無限に扱えるが、生成ロジックが有限範囲に閉じており、カメラや移動制限の実装次第となっている。

### 1-3. スケーラビリティ (多国家・多惑星化)
- **貿易システム (`trade.rs`)**:
  - **計算量**: すべての有効な貿易ルートに対して毎 Tick ループ処理を行っている。
  - **問題点**: 惑星数 $P$ が増えると、全結合に近い貿易網ではルート数が $P^2$ で増加する。
  - **距離計算**: 毎 Tick `distance_to` を再計算しており、星系が移動しない前提であれば無駄が大きい。
- **戦争・外交**:
  - 国家数 $N$ が増えると、二国間関係 ($N^2$) の計算コストが増加する。現状はループ内で関係を検索している箇所が見受けられる。

---

## 2. 改善提案

### 2-1. 惑星データの完全なプロシージャル生成
`GalacticCatalog` 生成時、または星系発見時に、Seed値に基づいて決定論的に惑星データを生成するロジックを追加する。

```rust
// 疑似コード: 惑星生成ロジックの追加
fn generate_planets(rng: &mut ChaCha20Rng, system_pos: Position) -> Vec<PotentialPlanet> {
    let num_planets = rng.gen_range(1..=5);
    (0..num_planets).map(|i| {
        // 恒星からの距離（重力や温度に影響）
        let orbit_dist = rng.gen_range(0.5..10.0); 
        PotentialPlanet {
            name: format!("Planet-{}", ["I", "II", "III", "IV", "V"][i]),
            environment: generate_environment(rng, orbit_dist), // 環境生成
            resources: generate_resources(rng), // 資源生成
            // ...
        }
    }).collect()
}
```

### 2-2. オンデマンド実体化 (Lazy Spawning)
初期化時に数千のエンティティをすべて `spawn` すると起動時間が長くなり、ECSのオーバーヘッドも増える。
- **提案**: `PotentialSystem` は軽量なデータ (`Resource`) として保持し、**探索 (`exploration.rs`) で発見されたタイミングでのみ ECS エンティティとしてスポーン**する（現状の実装方針を維持しつつ、中身を充実させる）。

### 2-3. スケーラビリティ対策: 空間インデックスとキャッシュ

#### A. 貿易ルートの動的制御
全惑星間の距離を計算するのではなく、**「通商圏 (Trade Network)」** または **「最大貿易距離」** を導入し、近隣の惑星間のみルートを結ぶ。
- 遠方の惑星へは、ハブ惑星を経由する（グラフ理論的な最短経路探索はコストが高いので、まずは「近隣限定」で $O(N)$ に抑える）。

#### B. 距離計算のキャッシュ化
`StarSystem` エンティティが移動しない場合、距離は不変である。
- `TradeRoute` コンポーネントに `distance` を永続化し、再計算を避ける。
- もし星系が移動する場合でも、`Transform` の `Changed` フィルタを使って更新が必要な場合のみ再計算する。

#### C. システムの実行頻度調整 (Tick Skipping)
全てのシステムを毎 Tick (60 FPS相当) で実行する必要はない。
- **貿易・経済**: 1秒に1回 (60 ticks) 程度で十分。
- **探索**: 現状でも 50 ticks に1回となっている (Good)。
- **AI思考**: 負荷分散のため、Tickごとに数カ国ずつ順番に処理する。

### 2-4. マップの「端」の処理
有限マップであることをゲームシステムに組み込む。
- **航行限界**: 銀河中心からの距離 $R > 150.0$ のエリアは「深宇宙 (Deep Space)」とし、航行速度ペナルティやスリップダメージを与えることで、プレイヤーを自然にマップ内に留める。

## 3. 今後のロードマップ
1.  **Phase 1**: `world_init.rs` の修正。`PotentialSystem` に `generate_planets` 処理を追加し、発見時に惑星がスポーンするようにする。
2.  **Phase 2**: `trade.rs` の最適化。距離計算のキャッシュ利用と、実行頻度の低下 (Every 10-60 ticks)。
3.  **Phase 3**: 大規模シミュレーション (100星系規模) でのプロファイリングと、空間分割 (QuadTree/OctTree) の導入検討。
